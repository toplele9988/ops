# 怎么设计、施工、测试、交货

问题：需求靠聊天口头传递，说到哪做到哪，漏掉的东西没有人发现。办法：让需求、设计、施工、测试、验收共用同一份清单，并且你随时能看到。

## 1. 需求账本是唯一的事实来源
- 位置：系统里「需求与验收」页，源文件 `web/src/data/requirements.json`。
- 每条：编号、你说了什么、现状、**怎么验收**（用一句普通话说清楚怎么检查它做好了）、下一步。
- 你提新要求：我**先加进账本，再动手**，并把我理解的复述给你。你看到的是账本，不是我的记忆。
- 每次会话开始我先读账本，结束时更新。账本里没有的东西，不算做过。

## 2. 设计：一页纸
每个功能先写：给谁用、每天怎么用、数据从哪里来、做不到什么。写在 `docs/`，你不用读，但我和 Codex 都按它做。

## 3. 施工分工
| 谁 | 做什么 |
|---|---|
| Claude（我） | 拆需求、设计、写关键部分、审查别人的代码、整合、上线 |
| Codex | 按任务书写后端和测试，不碰生产 |
| DeepSeek / Qwen | 系统里的批量整理、起草 |
任务书必须写清：允许改哪些文件、验收测试、真实数据只读、不得编造字段名（**必须先读真实源码核对**——这条是吃过亏的：任务书里猜错一个配置字段名，整个 WhatsApp 都读不到）。

## 4. 测试：四层，缺一层不算完成
1. 虚构数据的自动测试（每次改动都跑，全部历史测试必须继续通过）。
2. **真实数据只读预演**：用你的真实数据在本机跑一遍，不写生产、不发消息。这一层专门抓"测试通过但真实数据不对"的问题（例如：待回复被"Ok"撑大、图片没归档、日期显示成 1970 年）。
3. 真实浏览器截图：用与线上相同的安全响应头，看实际页面。
4. 你的验收：按账本里的"怎么验收"逐条点。我没有你的登录验证码，所以这一层只能是你。

## 5. 交货
一次交付只说四件事：新增了什么、怎么用（三句话）、你怎么验收、已知没做到的。不再写长文。
- 上线前备份、写回滚办法；
- 上线后核对路由表和服务状态；
- 更新账本里的状态。

## 6. 不会做的事
- 不替你向任何客户或供应商发消息（包括测试消息）。
- 不在没有你点击的情况下发送任何内容。
- 不绕开已确认的限制（阿里登录留在 Win10，网络分流只读）。
